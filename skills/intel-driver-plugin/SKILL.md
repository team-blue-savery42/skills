# Level Zero driver plugin

`LevelZeroPlugin.so` implements Modular's HAL C ABI (`SDK/include/HAL/*.h`)
on Level Zero. MAX's runtime, built with `--//:hal_device_context=true`,
loads it from `MODULAR_DRIVER_PLUGINS` (`level_zero@<path>`). Paths below
are relative to the fork's root; the plugin is in `plugins/intel/driver/`.

It assumes an Intel GPU host with compute-runtime and the Level Zero loader
(skill `intel-gpu-environment`) and a build (skill `mojo-max-intel-build`).

## Boundaries

- `Target/README.md` and `SDK/include/HAL/README.md`: a HAL plugin only
  translates each `M_driver_*` call into vendor driver calls. Caching,
  reference counting and other logic that is not specific to the hardware
  belongs above the HAL. When you want such logic, first check whether it
  is something Level Zero itself forces (see the allocation cache's comment
  in `Plugin.h` for an example of the argument made in the code).
- Dependencies: `driver/BUILD.bazel` uses `//SDK:HAL`, `//Target:Support`,
  LLVM `Support`, `dlpack` and the pinned Level Zero headers
  (`level_zero.MODULE.bazel`), the same kind of set as the in-tree CUDA and
  HIP plugins in `Target/BUILD.bazel`. Do not add MLRT or other mono-repo
  dependencies.
- The loader is not linked: `ZeApi.h` resolves every entry point from
  `libze_loader.so.1` with `dlopen` (the HIP plugin's pattern). A new Level
  Zero call goes into `MOJO_INTEL_ZE_REQUIRED`, `MOJO_INTEL_ZE_OPTIONAL` or
  `MOJO_INTEL_ZES_OPTIONAL` there.
  Read `/usr/include/level_zero/ze_api.h` for its signature.
- `Stubs.cpp` is generated by `plugins/intel/utils/gen-hal-stubs` from
  `SDK/include/HAL/M_driver_hal_symbols.inc`: every HAL symbol must exist
  for the conformance suite. Regenerate it when the HAL headers change or
  when you implement a stubbed entry point:
  `plugins/intel/utils/gen-hal-stubs . <implemented name>... > plugins/intel/driver/Stubs.cpp`
  (usage in the script's docstring; every implemented entry point must be
  listed, or it gets a stub).
- Two entry-point families sit outside the HAL C API, resolved by name from
  MAX's Intel HAL extension (`max/mojo/max/_driver/max_license/hal/extensions/intel.mojo`):
  device features (`IntelDeviceFeatures.h`) and device graphs
  (`IntelGraphs.h`). Both are versioned; append fields, never reorder.

## What it implements

File by file (each starts with a comment describing it):

- `Driver.cpp`: driver and device enumeration (`zeInitDrivers`, GPUs only),
  arch name from the IP version (`archName`: `bmg-g31`, `bmg-g21`,
  `arl-s`, `rpl-p`, else the dotted IP version), `M_driver_status_message`.
- `Context.cpp`: contexts (a `ze_context` plus an in-order immediate list
  for synchronous copies and fills), USM device and pinned host memory,
  queues (one in-order immediate command list each, on the compute engine),
  events (counter-based where the driver has them), copies, fills,
  synchronous frees, the allocation cache, graph capture.
- `Module.cpp`: bundles (`zeModuleCreate` from SPIR-V; IGC compiles at load
  with `kBuildFlags`), functions, launches. It reads the SPIR-V directly to
  find kernels whose last parameter is the dynamic shared memory pointer the
  compiler plugin appends, points the exported `__mojo_intel_abort_flag` and
  `__mojo_intel_heap` globals at the context's flag and heap, and reports
  unresolved imports from IGC's build log.
- `Limits.cpp`: CUDA-style device and function attributes and occupancy
  from Level Zero properties (multiprocessor = Xe-core, warp = smallest
  sub-group size); `ComputeCapability.h`: IP version to compute capability.
- `DeviceFeatures.cpp`: DPAS, DP4A, 2D block I/O and sizes from Intel's
  experimental property structs (restated from compute-runtime's headers);
  unknown when the driver does not list the extension.
- `Profile.cpp`/`Profile.h`: launch profiling (below).
- `IntelGraphs.h` and `Context.cpp`: device graphs on Level Zero's
  record/replay graph extension; while a queue captures, freed memory goes
  to a graph pool that lives as long as any graph.

## Behaviour that matters

- **Residency.** Every allocation is made resident at allocation
  (`zeContextMakeMemoryResident`), as CUDA memory is. Without it, a kernel
  that reaches memory first through a pointer inside a struct (MAX's
  closures) lost writes or page-faulted. `memory_wrap` of a region inside a
  block the plugin allocated skips a second residency call.
- **Synchronous frees.** `memory_free_sync` and `memory_free_pinned` release
  memory only after the work queued so far on every queue of the context
  completes (`releaseAfterQueues`), as `cuMemFree` waits; `zeMemFree` does
  not wait and kernels still queued page-faulted. The free itself does not
  block: queues get a free mark (a barrier signalling a counter-based event
  from a small ring) and the last completing queue releases the block.
  Released blocks go to a per-context cache by capacity class.
- **Abort.** IGC has no trap. A kernel that calls `abort()` sets a host flag;
  the next synchronize fails, and keeps failing, like a CUDA context after a
  trap.
- **Lost device.** Waits ask `zeDeviceGetStatus` at most every millisecond
  and on failure; after a page fault every later wait fails with "the GPU
  was lost" (compute-runtime may report the interrupted work complete).
  After a fault the next process on the GPU may hang (skill
  `intel-gpu-fault-recovery`).
- **Errors at the HAL C ABI.** Entry points return `M_driver_status_t`, never
  throw, and never abort on bad input. Use the standard codes from
  `SDK/include/HAL/M_driver_common.h` for argument errors
  (`M_DRIVER_STATUS_BAD_CONTEXT`, `..._INVALID_ARG`, ...). For a message, call
  `M::Intel::fail(driver, text)` or `failZe(driver, "zeCall", result)`
  (`Plugin.h`): they create an ephemeral custom status on the driver whose
  text `M_driver_status_message` returns once. Name the Level Zero call and
  its result, as `failZe` does. A partly built object is torn down before
  returning an error (see `M_driver_context_create`).
- **Copies on the compute engine.** Queue copies use the compute engine
  unless `MOJO_INTEL_COPY_OFFLOAD=1`; the reason is in `Context.cpp` at
  `M_driver_queue_create`.

## Environment switches

From the sources (`grep -n getenv plugins/intel/driver/*.cpp`):

| Variable | Where | Effect |
|----------|-------|--------|
| `MOJO_INTEL_PROFILE=<prefix>` | `Profile.cpp` | write `<prefix>.<pid>`, one record per launch, copy, sync, allocation, graph launch; format in `Profile.h` |
| `MOJO_INTEL_PROFILE_DEVICE=0` | `Profile.cpp` | host times only, no timestamp event per command |
| `MOJO_INTEL_COPY_OFFLOAD=1` | `Context.cpp` | copy-offload hint on queues |
| `MOJO_INTEL_HEAP_SIZE=<bytes>` | `Module.cpp` | device heap size for kernel `malloc` (decimal, 1 to 2^62) |
| `MOJO_INTEL_IGC_OPTIONS=<opts>` | `Module.cpp` | extra IGC options after `kBuildFlags`, e.g. `-cl-opt-disable` |
| `MOJO_INTEL_ALLOC_CACHE_MB=<n>` | `Context.cpp` | allocation cache limit (default 4 GiB; 0 turns it off) |
| `MOJO_INTEL_DEBUG_ALLOC_FILL=<byte>` | `Context.cpp` | fill new allocations (0xff gives NaNs) to expose reads of unwritten memory |
| `MOJO_INTEL_DEBUG_DRAIN_FREES=1` | `Context.cpp` | synchronous frees drain every queue first |
| `MOJO_INTEL_DEBUG_NO_FREE_REUSE=1` | `Context.cpp` | no reuse of blocks whose free is still pending |
| `MOJO_INTEL_DEBUG_MEMLOG=<file>` | `Context.cpp` | log every allocation and free, to match a fault address |

Most are read once per process; `MOJO_INTEL_IGC_OPTIONS` is read at each
module load and `MOJO_INTEL_HEAP_SIZE` when a context creates its heap.

## Tests

```sh
# HAL conformance suite (//Target:DriverPluginTests) plus Level Zero tests; needs an Intel GPU.
./bazelw test //plugins/intel/driver:LevelZeroPluginTest
./bazelw test //plugins/intel/driver:LevelZeroProfileTest   # own binary: the variable is read once
./bazelw test //plugins/intel/driver:ComputeCapabilityTest  # no GPU needed
# Manual: latency of HAL operations, prints only.
./bazelw test //plugins/intel/driver:LevelZeroPluginBench
```

`LevelZeroFaultTest` (tags `manual`, `exclusive`) page-faults the GPU on
purpose; the process after it may hang. Run it alone and only when you
work on fault handling (skill `intel-gpu-fault-recovery`).

Test kernels are SPIR-V binaries in `driver/test/data/`. The ones made from
`tests/codegen/*.spvasm` give their `spirv-as` command in the `.spvasm`
header; most others have the names of kernels in
`tests/codegen/kernels.mojo` (how they are regenerated is not documented;
not verified). End-to-end coverage through Mojo is in `utils/check-e2e`
and `utils/run-e2e <name>` (skill `intel-plugin-checks`).

## Debugging

- Read the status message first; it names the failing Level Zero call.
- Fault addresses: `MOJO_INTEL_DEBUG_MEMLOG` plus `journalctl -k` (the
  plugin's lost-device message points there).
- Use-after-free suspicions: `MOJO_INTEL_DEBUG_DRAIN_FREES=1`,
  `MOJO_INTEL_DEBUG_NO_FREE_REUSE=1`, `MOJO_INTEL_ALLOC_CACHE_MB=0`. If the
  problem goes away, look at the free marks and pending frees in
  `Context.cpp`.
- Plain Level Zero reproductions without Mojo: `plugins/intel/utils/l0/`
  (`run.sh <module.spv> <kernel>` runs one kernel; `copyrt.c`, `ext.c`,
  `markorder.c` probe copies, driver extensions and event ordering; each
  file's header gives its build command).
- Kernel launches that a loader-level tracer misses: `unitrace` traces the
  loader, but the plugin's profile (`MOJO_INTEL_PROFILE`) sees what MAX's
  graph runtime launches (`Profile.h`).
- Level Zero validation layer (`ZE_ENABLE_VALIDATION_LAYER=1`): Arch
  Linux's packaged layer (`level-zero-loader 1.32.0-1`) crashes at load;
  and the handle-lifetime and events checkers report false errors for
  immediate command lists and counter-based events. Details, versions and the workaround (a source-built
  loader and layer first on `LD_LIBRARY_PATH`) are in
  `plugins/intel/docs/intel-tools-issues.md`, section "Level Zero: the
  packaged validation layer crashes at load".

## Pitfalls

- Level Zero has no per-thread current context; "current" is plugin
  bookkeeping (`Context.cpp`).
- A kernel's arguments and group size live on the kernel object; a launch
  holds the function's mutex from setting them to appending.
- MAX may unload a bundle before its functions; `LoadedModule` is shared so
  the module outlives its kernels.
- Level Zero cannot tell "module has no such global" from a failed lookup;
  check the module's export list first (`LoadedModule::exported`).
- Integrated GPUs with `i915`: allocations over 4 GiB fail even with the
  relaxed-limits request (`plugins/intel/README.md`).
- Do not stop other users' GPU processes to free the device without the
  contributor's say-so (`AGENTS.md`).
